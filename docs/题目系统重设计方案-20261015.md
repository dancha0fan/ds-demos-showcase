# 题目系统重设计方案（2026-10-15）

> 状态：P0 已随本轮实施（独立出题 + 零作品展示 + 同题折叠 + 对比复用）；P1/P2 为建议路线，未实施、未迁移任何生产数据。

## 一、现状盘点（基于 feature/image-works @ 8c72cce 核实）

### 1. 数据模型

| 实体 | 说明 |
|---|---|
| `tasks` | 题目实体：`slug`（稳定 ID，URL 即 `/tasks/{slug}`）、`title`、`description`（题面）、`category`、`status`（candidate/active/merged/hidden）、`merged_into_id` |
| `demo_tasks` | 作品 ↔ 题目**多对多**（决策 D1）：一件作品可挂多题，一题可有多件作品 |
| `entity_suggestions` | 统一建议收件箱：`kind=new_task / task_match / merge_task…`，批准才落库（`suggestion_service.review`），本表永不直改实体 |

关键不变式（治理口径）：**用户贡献候选，管理员决定知识体系**。上传时声明挂题或提议新题都只产生 pending 建议；直建 Task 是管理员专属（`POST /admin/tasks`）。

### 2. 题目产生路径（本轮之前）

1. 管理员手工建题（active 直出）；
2. prompt 簇「成题」（规则层建议 → 收件箱 → 批准）；
3. 上传时 `task=slug`（挂既有题，候选待审）或 `propose_task={title,…}`（提议新题，候选待审）。

**题目不能脱离作品存在** —— 没有任何一条路径允许先立题后交作品。这正是本轮要解的题。

### 3. 消费路径

- `GET /tasks`：公开只出 active（candidate 仅管理员）；
- `GET /tasks/{slug}`：详情 = 按模型对比（Benchmark 行）+ 逐件证据（chain 行，服务端算题面一致性）+ 并排看数据（rows 带 `cover_url` 与本轮新增 `demo_type`）；
- 作品列表（`GET /demos`）每行已带 `tasks:[{id,slug,title}]`（serializers.py `serialize_demo`），作品库同题分组因此**纯前端可做**。

## 二、本轮已实施（P0）

### 1. 独立出题（题目与作品创建解耦）

- 新端点 `POST /api/v1/tasks`（`routers/tasks.py::propose_task`）：登录必须（`current_user`，匿名 401），body 校验（title 1–200 必填、description ≤4000、category ≤64）；
- **只落 pending `EntitySuggestion(kind=new_task, source=user)`，不直建 Task** —— 与上传 `propose_task` 走同一收件箱、同一批准代码路径（`suggestion_service.review` → `create_task(status=active)`），权限面与审核语义零新增；
- 限流：每用户每小时 10 次（全站 ratelimit 单一实现）；
- 防重：与 active 题目**逐字同名** → 409 并指路既有 slug（按标题模糊猜同题仍然不做）；同用户同题名 pending → 幂等返回不堆箱；
- 配套修复：`suggestion_service.create` 增加 `dedupe=False` 逃生口 —— 原去重键 `(kind, ref_id, demo_id)` 对独立出题三条全 None，会把全站提案判成同一条。既有调用方默认行为不变。
- 前端：`/tasks/new`（登录门槛，路由守卫接管匿名跳登录）+ 题目列表页「＋出题」入口 + mock 同步。

### 2. 零作品题目正常展示

详情页 compare/chain 双空态**本就成立**（`demos_total=0`、`rows=[]` 渲染空态而非报错）；本轮给两处空态补了显式「挑战此题」CTA（`/upload?task=slug`），空态即入口 —— 自己或他人后续关联作品走既有挂题申请流程，批准后生效。

### 3. 作品库同题折叠（前端呈现层）

- 分组纯函数 `utils/demoList.ts`：分组身份 = **稳定 task.id**；一件作品挂多题时的单归属策略：**当前筛选题目（URL `?task=`）优先，否则 id 最小**（与后端返回顺序无关、跨页确定）；**不按标题猜同题**；
- 组序 = 各组首件在当前排序中的位次 → 最新/最热/随机的排序语义原样保留；筛选/分页完全不动（服务端分页不变，分组只作用于已加载切片）；
- **口径诚实**：组内计数是已加载切片数，组头标注「已加载 N 件」，不冒充题目总件数；
- 多件真题组默认收起 = 题名 + 已加载数徽章 + 前 3 张封面摘要，可展开为完整瀑布；单件组与「未挂题」组原样平铺；开关记忆在 localStorage，默认开；展开态随返回恢复快照一并还原。

### 4. 同题对比复用（不重做）

图像一期的并排看（勾选 2–4 件、数据全来自 chain.rows、服务端只出 approved）对**任何带封面作品通用**。本轮补齐语义显性化：

- chain 行新增 `demo_type`（`task_service.task_chain` 一行 + schema/TS/mock 同步）；
- 并排看每格加类型徽章：**图像 = 看图比较；网页/文件包/外链 = 看封面 + 点进作品实跑**。两种口径同屏混排时一眼可辨，不冒充同一基准。

### 5. 瀑布流健壮性（作品库）

- **重复/漏项的根修在后端（会话固定种子）**：`sort=random` 新增可选 `rs` 参数 —— 带种子时按种子确定性洗牌、无视 60s 时间桶，整段翻页建立在同一次洗牌上，跨桶**不重复不漏件**；无 `rs` 的调用保持旧行为（60s 缓存整份随机序，兼容首页「随便看看」），但响应回传当前有效种子（`Paginated.random_seed`），客户端可选择 pin。前端「加载更多」回传种子，换筛选重新领种子；
- **客户端去重降级为兜底层**：`dedupeBySlug` 仍保留（防缓存/竞态重复），但漏项由种子机制根修，不靠前端补页；
- **滚动位置**：离开时按 query 签名快照「已加载页数 + 滚动位 + 随机种子 + 分组展开态」（sessionStorage），返回时先补齐加载深度再落点 —— 修复无限滚动返回被钳回第 1 页的经典坑；
- **布局抖动**：MasonryGrid 整体替换时清理旧列表高度缓存（避免陈旧高度让首帧排布失真）；卡片封面区 4:3 aspect-ratio 本就锚住高度；
- **失败重试**：加载更多失败的重试按钮既有，保留；移动端走既有单列自适应，未新增断点。

## 三、兼容性

- **零迁移**：没有改任何表结构；新端点只写既有 `entity_suggestions` 表；
- **零行为变化**：公开列表/详情、上传挂题、管理收件箱、审计链路全部原样；`suggestion_service.create` 新参数带默认值，既有调用方不受影响；
- 待审中的独立出题对公开面不可见（candidate 语义复用），批准前不影响任何人；
- 已有数据（题目、挂载、合并链）完全不动。

## 四、建议路线（未实施）

### P1 —— 出题体验补全

- 「我的出题」视图：登录用户查看自己提交的提案状态（pending/approved/rejected），被拒时可看理由；
- 出题页挂「相似题目建议」（复用 `GET /tasks/suggest`，提交前提醒既有同题）；
- 收件箱里 new_task 展示提案来源区分（上传提议 vs 独立出题）。

### P2 —— 题目生命周期

- 题主/管理员给题目补充分类词表约束（当前 category 自由文本）；
- 零作品题目长期无作品的回收策略（hidden 而非删除，可恢复）；
- 题目合并 UX 已有（admin dry-run + 审计），可考虑给提案者通知结果。

### 明确不做（红线不变）

- 不按标题自动合并题目/作品；
- 不给独立出题开匿名或免审通道；
- 不做综合排名结论（benchmark 红线）。
